# Assignment 1
## Stage 1
### 1. How the basline works  
For a $2\times2\times2$ cube, there are 8 corners, After fixing one corner, the remaining seven corners can be permuted freely, giving $7!$ possible permutations. Each corner has three possible orientations. However, the orientations are not independent because the total corner twist must satisfy
$$
\sum_{i=0}^{6} o_i \equiv 0 \pmod 3.
$$


So if we know the first six corner, the oriention of last one will also be determined, the number of states will be:
$$
7!\times 3^6=3,674,160
$$

The baseline represents each valid cube state using a dense integer rank. The permutation is encoded using a Lehmer rank $p$, where
$$
0\le p<7!=5,040,
$$
Lehmer rank $p$：
$$
p=\sum_{i=0}^{6} c_i(6-i)!
$$
c means :
$$
c_i=\sum_{j=i+1}^{6}[s.p[j]<s.p[i]]
$$


while the first six corner orientations are encoded as a base-3 value \(o\), where
$$
0\le o<3^6=729.
$$
The two values are then combined as
$$
\text{rank}=p\times729+o.
$$
This gives each valid cube configuration a unique integer index from $0$ to $3,674,159$.

To solve the cube, the baseline performs a complete breadth-first search starting from the solved state. During this search, it constructs a toward_solved[] table with one entry for every reachable state. When BFS first discovers a new state, the table records the inverse move that returns the state one step toward the solved state. Since all nine moves in the half-turn metric have equal cost, BFS discovers states in nondecreasing distance from the solved state and therefore provides shortest solution paths.

### 2. Invariants
* Permutation Invariants:
    The seven movable corner entries must form a valid permutation of the cubie indices $\{0,1,2,3,4,5,6\}$. Each numbers must appear exactly once, so duplicate or missing cubies represent an invalid state.
    
* Orientation Invariant:
The second is the orientation invariant. Each corner orientation must be one of
$$
0,\ 1,\ 2,
$$
and the total corner twist must satisfy
$$
\sum_{i=0}^{6}o_i\equiv0\pmod3.
$$
All legal generator moves preserve this modulo-3 constraint. Therefore, the seventh orientation contains no independent information and can always be reconstructed from the first six.
### 3. Baseline Cost
Three are three major memory structures are: `toward_solved`, `BFS queue` and `transition tables`

`toward_solved` table stores one move for each state. Since one byte is sufficient to encode the nine possible moves, the total size is
$$
3,674,160\times 1 = 3,674,160\text{ bytes}.
$$

The second structure is the `BFS queue`. Each state in the queue is stored as a 32-bit rank rather than as a complete cube state. The queue is sized for all \(3,674,160\) states:
$$
3,674,160\times4=14,696,640\text{ bytes}.
$$
The third structure is the set of `transition` tables. The solver separately precomputes quarter-turn transitions for the \(5,040\) permutation ranks and the \(729\) orientation ranks. Since only the three basic faces \(R\), \(B\), and \(D\) need to be stored, the total number of transition entries is
$$
3\times(5,040+729)=17,307.
$$
Each entry is stored as a 16-bit:
$$
17,307\times2=34,614\text{ bytes}.
$$
The remaining six moves, such as R2 and R', are generated by applying transition table multiple times

The total peak memory usage is therefore
$$
3,674,160+14,696,640+34,614=18,405,414\text{ bytes},
$$

And for the computational cost, the $3,674,160$ states is expanded using nine possible moves: $3,674,160\times9=33,067,440$

Each edge updates both the permutation and orientation transition components, resulting in$33,067,440\times2=66,134,880$ transition updates during table construction

### 4. Search Algorithm — IDA*
IDA* is like an upgraded version of iterative-deepening search. Iterative-deepening search initially assumes the current completion depth bound is 1 and attempts to find a solution; if not found, it continues to search 2, 3, 4...,

Back to IDA*, each node is defined as:
$$
g(s)=\text{moves already used}
$$
$$
h(s)=\text{lower bound on remaining moves}
$$
$$
f(s)=g(s)+h(s)
$$
Initial threshold:
$$
bound=h(start)
$$
During the search:
```
if g + h(state) > bound:
    prune
```

If a solution is not found in an entire search iteration, record the minimum among all nodes pruned by the threshold:
$$
f>bound
$$
and set:
$$
bound_{next}=\min\{f(s)\mid f(s)>bound\}
$$
Then search again from the root.

#### 4.1 IDA* Optimality

Let the true optimal solution cost be:
$$
C^*=d(start).
$$
Since the heuristic is admissible:
$$
h(start)\le C^*.
$$
Therefore, the first round's:
$$
bound=h(start)
$$
will not be greater than the true optimal solution length.
For any node $s$ on the optimal path, assume it has already taken:
$$
g(s)
$$
steps, and the true remaining distance is:
$$
d_{\text{remain}}(s).
$$
Because:
$$
g(s)+d_{\text{remain}}(s)=C^*
$$
And the heuristic satisfies:
$$
h(s)\le d_{\text{remain}}(s),
$$
Therefore:
$$
f(s)=g(s)+h(s)
\le
g(s)+d_{\text{remain}}(s)=C^*.
$$
So when:
$$
bound=C^*
$$
because nodes on the optimal path always satisfy $f(s) \le bound$, they will never trigger the $f(s) > bound$ pruning condition.

Therefore, IDA* will definitely find the optimal solution when the threshold reaches $C^*$.
In addition, if currently:
$$
bound<C^*
$$
then no solution with a length not exceeding the bound exists.
The next threshold for IDA* uses:
$$
bound_{next}=\min\{f(s)\mid f(s)>bound\}.
$$
Because for all optimal paths:
$$
f(s)\le C^*,
$$
the threshold will not skip all possible optimal paths.
Therefore, when the solved state is found for the first time, its solution length is:
$$
C^*
$$


### 5. Move Generation and Pruning

```
R, R2, R'
B, B2, B'
D, D2, D'
```

There are 9 possible moves as shown above. By utilizing same-face pruning, if the face of the previous move is R, the next step will not consider:

```
R
R2
R'
```

This is because any two consecutive same-face moves can either be:
- Combined into a single move, or
- Canceled out entirely.

With this modification, the branching factor is reduced from 9 to 6.

### 6. Heuristic

Define two heuristics:

$$
h_p(p)=\text{the shortest distance from }p\text{ to the solved permutation when only considering permutation}
$$

and

$$
h_o(o)=\text{the shortest distance from }o\text{ to the solved orientation when only considering orientation}.
$$

Finally, use:

$$
\boxed{
h(p,o)=\max\left(h_p(p),h_o(o)\right)
}
$$

#### 6.1 Permutation Heuristic

There are $7!=5040$ states.
Therefore, build the following on the host:

```
perm_dist[5040]
```

Next, starting from the solved state, use BFS to determine how far each state is from being solved. The concept is as follows:

```
for every p:
    perm_dist[p] = UNVISITED

perm_dist[solved_p] = 0
queue.push(solved_p)

while queue is not empty:
    p = queue.pop()

    for move in {R, R2, R', B, B2, B', D, D2, D'}:
        next_p = apply_perm_move(p, move)

        if perm_dist[next_p] == UNVISITED:
            perm_dist[next_p] = perm_dist[p] + 1
            queue.push(next_p)
```

Once completed:

$$
perm\_dist[p]
$$

is the minimum number of HTM moves required to solve the permutation back to the solved state without considering orientation at all.

#### 6.2 Orientation Heuristic

There are $3^6$ states, build:

```
ori_dist[729]
```

Similarly, perform BFS starting from the solved orientation:

```
for every o:
    ori_dist[o] = UNVISITED

ori_dist[solved_o] = 0
queue.push(solved_o)

while queue is not empty:
    o = queue.pop()

    for move in {R, R2, R', B, B2, B', D, D2, D'}:
        next_o = apply_ori_move(o, move)

        if ori_dist[next_o] == UNVISITED:
            ori_dist[next_o] = ori_dist[o] + 1
            queue.push(next_o)
```

Finally:

$$
h_o(o)=ori\_dist[o].
$$

#### 6.3 Admissibility Proof

Let the complete cube state be $s=(p,o)$, and the true optimal solution length be $d(s)$. Assume there exists an optimal solution:

$$
m_1,m_2,\dots,m_d
$$

where $d=d(s)$. This sequence of moves solves the complete cube, so after performing them, it must simultaneously satisfy:

$$
p\rightarrow p_{\text{solved}}
$$

and

$$
o\rightarrow o_{\text{solved}}
$$

Now, looking only at the permutation abstraction. The same sequence of $d$ moves is, of course, also a valid path from the current permutation $p$ to the solved permutation. Therefore, a solution of length $d$ must exist in the permutation abstraction. And since $h_p(p)$ is the shortest distance in this abstraction:

$$
h_p(p)\le d(s)
$$

Similarly, that same sequence of moves for the complete solution will definitely also solve the orientation, therefore:

$$
h_o(o)\le d(s)
$$

Since neither is greater than $d(s)$:

$$
h_p(p)\le d(s)
$$

$$
h_o(o)\le d(s)
$$

then the maximum of the two cannot exceed it either:

$$
\max(h_p(p),h_o(o))\le d(s)
$$

Therefore:

$$
\boxed{h(s)=\max(h_p,h_o)}
$$

is an admissible heuristic.

### 7. Explicit DFS Stack
The assignment has a restriction against using the heap or recursion, so IDA* cannot be implemented with a recursive DFS directly. Therefore, a fixed-size explicit stack must be used, as the HTM diameter is 11.
Each element in the stack needs to store:

```
p               current permutation rank
o               current orientation rank
next_move       下一個尚未嘗試的 move
last_face       上一個 move 的 face
```

The two 16-bit fields require two-byte alignment, so one frame occupies 6
bytes.  Twelve frames require:
$$
12\times6=72\text{ B}
$$

```
IDA*
```

### 2. Factored Search State and Transitions

The complete rank is useful for enumerating all states during host-side tests,
but IDA* keeps the two components separate:

```c
typedef struct {
    uint16_t p;
    uint16_t o;
} search_state_t;
```

Here, `p < 5040` and `o < 729`.  Since moves update these components
independently, the target only needs three quarter-turn tables:

```c
permutation[3][5040]
orientation[3][729]
```

`R2` and `R'` follow the corresponding quarter-turn table two and three times.
Each step reads one 16-bit entry from each table, so no physical cubie arrays
or ranking operations are needed in the search loop.  Exhaustive tests compare
all table-based moves with the original `source` and `twist` model, confirming
that factoring preserves the complete transition system.

### 3. Heuristic Tables and H1/H2

The host generator uses reverse BFS to build:

```c
perm_dist[5040]
ori_dist[729]
```

The target evaluates:

$$
h(p,o)=\max(perm\_dist[p],ori\_dist[o]).
$$

It costs two byte loads and one comparison.  H1 compares it with the baseline
BFS distance for all states:

$$
h(p,o)\le d_{BFS}(p,o).
$$

```text

H1: maximum heuristic = 7
H1: exact on 17108 states
```

H2 verifies that the solved entries are zero and that every abstract state was
visited:

```text
H2: permutation heuristic max = 7
H2: orientation heuristic max = 6
```

Thus the tables are complete and the combined heuristic is admissible.

### 4. Iterative IDA* Implementation

IDA* starts with `bound = h(start)`, prunes when `g + h > bound`, and uses the
smallest rejected value as the next bound.  Recursion is replaced with 12
fixed frames: one root plus at most 11 moves.

```c
typedef struct {
    uint16_t p;
    uint16_t o;
    uint8_t next_move;
    uint8_t last_face;
} ida_frame_t;
```

Each frame is exactly 6 bytes, so the DFS stack occupies:

$$
12\times6=72\text{ bytes}.
$$

Moves of the same face are not generated consecutively.  Any such pair either
cancels or can be replaced by one HTM move, so this pruning does not remove an
optimal solution.  The non-root branching factor falls from nine to six.  The
search uses neither heap allocation nor recursion.


Since BFS supplies exact HTM distances, this verifies optimality for every

### 7. RV32I-Oriented C Optimization

RV32I has no multiplication, division, or remainder instructions.  The C code
was therefore restructured so the normal solve path uses table lookup,
shift/add, and comparison instead of software arithmetic helpers.

#### 7.1 Move Decoding

Move decoding changed from:

```c
face = move / 3;
turns = move % 3 + 1;
```

to two nine-byte tables:

```c
face = move_face[move];
turns = move_turns[move];
```

Face pointer tables also select transition rows without multiplying by 5,040
or 729.

#### 7.2 Direct Component Encoding

The earlier input path constructed and immediately split a dense rank:

```text
rank = p * 729 + o
p = rank / 729
o = rank % 729
```

The new path computes `p` and `o` directly.  Fixed Lehmer radices use
shift/add, as does base-3 orientation accumulation:

```c
o = (o << 1) + o + digit;
```

Dense-rank division remains only in host generation and exhaustive tests.

#### 7.3 Modulo and Input Parsing

Corner twist `% 3` became a comparison and possible subtraction.  Splitting
the parser into two seven-character loops also removes its `i % 7` indexing.

#### 7.4 Combined Transition Loop

Permutation and orientation previously used separate loops.  Combining them
keeps the required `2t` table reads for `t` quarter turns but halves the
loop-control sequences:

```c
do {
    state.p = p_table[state.p];
    state.o = o_table[state.o];
} while (--turns != 0);
```

#### 7.5 Stack Addressing and Successful-Node Path

The search keeps a frame pointer instead of recomputing `stack[depth]`.
Push and pop therefore require only:

```text
push: frame += 6
pop:  frame -= 6
```

Both operations map to one `addi` on RV32I, so padding the frame to a
power-of-two size would not improve pointer traversal.  A six-byte stride is
still divisible by two, keeping both `uint16_t` fields aligned.  Checking
solved before the heuristic also skips two byte loads, the maximum, and the
threshold comparison on the successful child.

#### 7.6 Operation-Count Summary

These are C-level hot-path counts.  Compiler effects and target performance
will be measured with Ripes after assembly translation.

| Operation | Before | After |
|---|---|---|
| Decode move face | Division by 3 | Byte-table lookup |
| Decode turn count | Remainder by 3 plus one | Byte-table lookup |
| Encode input state | Dense rank followed by `/729` and `%729` | Direct component ranks |
| Orientation reduction | `%3` | Compare/subtract |
| Parse destination index | `i % 7` | Two fixed loops |
| Transition table reads for `t` turns | `2t` | `2t` |
| Transition loop-control sequences | Two per turn | One per turn |
| DFS frame addressing | Six-byte indexed stride | Six-byte pointer increment/decrement |
| Successful child heuristic | Two loads plus max and comparison | Skipped |

### 3. Functional Assembly IDA* Solver

The next refinement connects the parser to the static transition and
heuristic tables, the iterative IDA* search, and an independent replay of the
returned path.  The search uses twelve six-byte frames and an eleven-byte
solution buffer.  It has no recursion, dynamic allocation, or dependency on a
runtime stack pointer.

Each move selects one of the three permutation and orientation rows, follows
the row one to three times, and loads the next component ranks with `lhu`.
The row byte offsets 10,080, 20,160, 1,458, and 2,916 are constructed with
`lui`, `addi`, and `add`; no multiply is hidden in address calculation.  The
same-face pruning and smallest-rejected-bound update are the same operations
verified by H3 in the C implementation.

The production source embeds one arbitrary state at `input_state`.  It parses,
solves, and replays that state, then leaves the solution length in `x30` and a
pass flag in `x31`.  The generated test source instead solves the three fixed
states, checks exact lengths 0, 1, and 11, replays every path, and rejects all
nine invalid inputs.  Thus the distance-11 case checks both optimal length and
the target's actual returned path rather than a pre-recorded solution.

```bash
make rv32i_solver.s
make check-rv32i-asm
```

The default production input is the distance-11 vector.  Its `RV32_ISS`
result was:

| Retired instructions | Cycles | `x30` | `x31` |
|---:|---:|---:|---:|
| 18,816,530 | 18,816,530 | 11 | 1 |

The complete internal regression produced:

| Ripes model | Retired instructions | Cycles |
|---|---:|---:|
| `RV32_ISS` | 18,819,059 | 18,819,059 |
| `RV32_5S` | 18,819,058 | 23,539,651 |

Both models set `x31` to one.  The one-instruction difference is the models'
handling of program termination; all solver and replay checks agree.  These
results establish T5 for the embedded test paths, T6 for the known
distance-11 vector, and cross-model agreement for the three required local
cases.  The GCC `-O2` comparison and linked `.text` size remain open until a
RISC-V cross-compiler is available.
